# Как предложить модуль

Это источник модулей от автора Aster Mail и место для предложений сообщества.
Откройте issue с описанием сценария или pull request с модулем в отдельной папке.
Публикация здесь не означает автоматическую проверку безопасности или включение
модуля в Aster Mail.

Прочитайте [руководство разработчика](docs/DEVELOPMENT.md), [SDK](docs/sdk/README.md),
[правила проверки безопасности](docs/SECURITY-REVIEW.md) и [AGENTS.md](AGENTS.md).
Политика проекта и приватное сообщение об уязвимостях — в [SECURITY.md](SECURITY.md).
Новые возможности host оформляйте отдельным изменением
контракта. В pull request включите:

- `module.json`, готовые браузерные JS/HTML/CSS и явный список `files`.
- README: назначение, совместимость, установка, настройка, права сервиса и ограничения.
- LICENSE/NOTICE для кода и ресурсов с сохранением атрибуции. Не включайте секреты
  и проприетарные SDK без права распространения.
- Проверки успеха, отказов, неопределённых записей, смены аккаунта и отказа в правах.
- Для UI — снимки, клавиатуру, светлую/тёмную тему, масштабы 100/150/200%.

Используйте минимальные права и точные HTTPS origins. Панели должны быть адаптивными,
с подписями полей, загрузкой и явными ошибками. Не меняйте DOM основного приложения,
не отправляйте письма/приглашения: предлагайте изменения в черновик для проверки
пользователем. Не используйте реальные почтовые ящики для тестов отправки.

Повышайте версию пакета при изменении файлов. Проверяйте его авторитетным
`scripts/check-module.cjs` совместимого SDK Aster Mail.

## Pull request с новым модулем

1. Создайте fork и ветку `codex/<module-name>` или другую понятную рабочую ветку.
2. Добавьте модуль в отдельную папку; подготовьте документацию, лицензию и тесты.
3. Зафиксируйте пакет отдельным коммитом и подготовьте кандидат записи каталога
   с pin этого коммита. В PR из fork приложите его к описанию PR; действующий
   `catalog.json` обновит сопровождающий после приёмки пакета. Порядок и проверки
   описаны в [DEVELOPMENT.md](docs/DEVELOPMENT.md).
4. Выполните `npm run check`, `npm test`, `npm run check:catalog`, проверку пакета
   валидатором host и нативные проверки затронутых сценариев.
5. Откройте PR в `main` этого репозитория. Опишите назначение, права, передаваемые
   данные, внешние записи, поведение после сбоев, совместимость и результаты проверок.
6. Ответьте на review и обновите commit pin/fingerprint, если изменился пакет.

Каждый PR с новым модулем проходит [security review](docs/SECURITY-REVIEW.md).
Автор предоставляет доказательства проверок; проверяющий повторно изучает пакет
и запись каталога. Изменения SDK рассматриваются отдельно в Aster Mail.
Окончательное решение о приёмке и выпуске принимает владелец репозитория.
Не создавайте release tag в PR: выпуск оформляется после приёмки.

## Лицензирование вклада

Новый код и документация предлагаются на условиях [MIT License](LICENSE)
этого репозитория. У автора должны быть права на предлагаемый вклад.
Сохраняйте copyright и LICENSE/NOTICE заимствованных компонентов; перечисляйте
их источники и лицензии в пакете. Не добавляйте код с неясным происхождением
или условиями распространения, несовместимыми с публикацией пакета.

Сообщение об ошибке должно содержать версию модуля и Aster Mail, ОС, шаги
воспроизведения и ожидаемый результат. Используйте вымышленные данные.
Для предложения модуля укажите сервис, сценарий, официальный API, нужную
авторизацию и предполагаемые права. Не прикладывайте токены и корпоративные ответы.
