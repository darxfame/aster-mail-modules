# Разработка модулей Aster Mail

Это руководство описывает полный путь от исходников до предложения модуля
в каталог. Установка для пользователей описана в [README](../README.md).

## Рабочее окружение

Нужны Git и Node.js 22 или новее. Для нативных проверок дополнительно нужна
рабочая копия Aster Mail с SDK, который поддерживает возможности вашего пакета,
и установленные зависимости этого приложения, включая Electron.

```sh
git clone https://github.com/darxfame/aster-mail-modules.git
cd aster-mail-modules
npm ci
npm run check
npm test
npm run check:catalog
```

Этот репозиторий самостоятелен: у него своя Git-история, версии и каталог.
Для совместной работы с исходниками приложения его можно разместить в
`owamail/aster-mail-modules/`. Перед изменениями прочитайте [AGENTS.md](../AGENTS.md)
и актуальные правила рабочей копии Aster Mail. Вложенную папку исключите из Git
родительского проекта. Команды Git для модулей выполняйте из этого репозитория.

## Контракт и границы модуля

Начните с [архитектуры SDK](sdk/architecture.md),
[справочника API](sdk/development.md) и [схемы manifest](sdk/module.schema.json).
Опишите сценарий, используемые данные, запросы, внешние записи и необходимые права.
Если SDK не покрывает сценарий, сначала предложите изменение его контракта
в основном репозитории Aster Mail. Не обходите ограничения из кода пакета.

Код пакета — браузерные ES modules. Node.js, Electron, прямой файловый доступ,
произвольная сеть и DOM основного приложения недоступны. CommonJS `.cjs`
используется только для утилит и Node-тестов этого репозитория.

## Структура пакета

Создайте отдельную папку с коротким именем сервиса или назначения:

```text
my-module/
  module.json
  main.js
  panel.html
  panel.js
  panel.css
  README.md
  LICENSE
test/
  my-module.test.cjs
```

HTML/CSS и представления нужны только модулям с собственным UI. `files` в manifest
перечисляет все необходимые ресурсы пакета; `module.json` включается автоматически.
Необъявленные файлы не устанавливаются. Не включайте сборочные инструменты,
временные данные, ключи или исходники Aster Mail в устанавливаемые ресурсы.

Выберите уникальный ID, например `company.meetings`, и семантическую версию
`1.0.0`. Команды и представления имеют уникальные ID внутри пакета. Объявите
только нужные права, точные HTTPS origins и необходимые `x-*` заголовки.
Wildcard origins и перенос учётных данных Exchange запрещены.

Основная точка входа экспортирует `activate(api)` и возвращает обработчики
объявленных команд. Побочные эффекты активации ограничены подготовкой состояния;
создание объектов во внешнем сервисе выполняется только по действию пользователя.

Рабочий пример интеграции — [ktalk](../ktalk/README.md). Контракты запуска приложения
и корпоративного входа описаны в [extensions.md](sdk/extensions.md).

## Оформление и доступность

- Два пробела, точки с запятой, понятные camelCase-имена; код и комментарии на английском.
- Русский и английский UI — через словарь модуля. При интеграции интерфейса Aster Mail
  используйте его общий `src/i18n.js`. Содержимое почты, имена и протокольные поля не переводятся.
- Локальные HTML/CSS/JS без CDN, inline handlers, `eval`, iframe, workers и native addons.
- Панель подстраивается под контейнер host, тему и масштаб; фиксированные desktop-размеры
  и вмешательство в DOM/CSS основного приложения не допускаются.
- У полей есть подписи, у кнопок — понятное назначение. Нужны видимый focus,
  управление клавиатурой, доступная прокрутка и объявляемые состояния загрузки/ошибки.
- Проверяйте 100/150/200%, светлую и тёмную темы, узкую ширину и длинные значения.
  Не выдавайте интерфейс модуля за системное подтверждение Aster Mail.

## Состояние, секреты и записи

Настройки сохраняются через SDK в зашифрованное хранилище Aster Mail, отдельно
для модуля и аккаунта. Секреты не сохраняются в файлы пакета, renderer storage,
логи и результаты команд. Данные передаются сервису только по назначению сценария.

Не повторяйте внешнюю запись после timeout, разрыва, неопределённого ответа
или перезапуска. Сохраните намерение до записи и результат для отдельной проверки.
Проверяйте документацию сервиса: upsert нельзя выдавать за безопасный create-only.
Результат внешней операции не разрешает автоматически отправить приглашение.
Модуль предлагает правки актуальному черновику; пользователь проверяет и отправляет его.

## Проверки до PR

Обязательны синтаксис и Node-проверки:

```sh
npm run check
npm test
npm run check:catalog
```

Проверьте пакет авторитетным валидатором SDK из рабочей копии Aster Mail:

```sh
node /path/to/aster-mail/scripts/check-module.cjs /path/to/aster-mail-modules/my-module
```

Для существующей интеграции Толка:

```sh
ASTER_MAIL_HOST=/path/to/aster-mail npm run check
ASTER_MAIL_HOST=/path/to/aster-mail npm run check:catalog
ASTER_MAIL_HOST=/path/to/aster-mail /path/to/aster-mail/node_modules/.bin/electron scripts/test-native.cjs
```

В PowerShell задайте `$env:ASTER_MAIL_HOST` и запускайте `electron.cmd` из
`node_modules/.bin` рабочей копии приложения. Путь должен указывать на SDK,
поддерживающий проверяемый контракт. Fixture Толка не заменяет нативные проверки
другого модуля: добавьте проверку его собственных границ и сценариев.

Покройте нормальный успех и отказы: неверный ввод, отсутствие прав, 401/403/429/500,
redirect, timeout, неверный JSON, обрыв после записи, отзыв/истечение сессии,
закрытие панели, смену аккаунта и устаревший редактор. Проверяйте отсутствие
повтора записи и сохранность уже введённых данных. Непроверенное укажите в PR.

Для изменений host дополнительно выполняются его `npm run check`, `npm test`,
`npm run test:modules` и `npm run test:connection`. Поведение платформенных API
проверяется в настоящем Electron. В тестах используются вымышленные данные;
отправка писем и приглашений в реальный ящик запрещена.

## Предложение и публикация

Порядок PR описан в [CONTRIBUTING.md](../CONTRIBUTING.md), review безопасности —
в [SECURITY-REVIEW.md](SECURITY-REVIEW.md), формат записи — в [CATALOG.md](CATALOG.md).

1. Подготовьте исходники, README, LICENSE/NOTICE и проверки в отдельной ветке.
2. Зафиксируйте готовый пакет отдельным коммитом. Вычислите fingerprint валидатором
   host на этом snapshot. Проверьте, что рабочая копия пакета ему соответствует.
3. В следующем коммите добавьте запись `catalog.json`, ссылающуюся на полный SHA
   предыдущего коммита, с точными SHA-256, правами, origins и требованиями к SDK.
4. Повторно проверьте каталог и откройте PR с результатами. Каталог не должен
   ссылаться на ветку, mutable tag или собственный ещё не созданный commit.
5. Если пакет изменился при review, обновите pin и fingerprint. Для уже
   опубликованной версии изменённые ресурсы требуют новой версии пакета.

Для внешнего участника с PR из fork кандидат записи прикладывается к описанию PR.
Не меняйте действующий каталог на недоступный в авторском репозитории commit.
Сопровождающий переносит принятые коммиты в историю этого репозитория, добавляет
запись каталога и оформляет выпуск до атомарной публикации ветки и нового тега.
Это позволяет проверить immutable источник и не требует от автора PR прав на выпуск.

Для модуля в другом репозитории укажите доступный публичный immutable commit.
Проверяющий скачивает snapshot именно из указанного источника. CLI `check:catalog`
этого репозитория проверяет локальную Git-историю авторских модулей; для внешнего
источника используйте загрузчик клиента и авторитетный валидатор SDK.

Версия репозитория и версия отдельного пакета независимы. Выпуск репозитория
обновляет `package.json`, `package-lock.json`, русские release notes и создаёт
новый annotated tag `v<version>` на финальном коммите. Ветку и конкретный новый
тег публикует владелец атомарно. Существующие теги и выпущенные пакеты не заменяются.
